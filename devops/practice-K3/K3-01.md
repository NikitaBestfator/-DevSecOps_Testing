# K3-01. CI/CD и ветки

## 1. Четыре элемента процесса в моём проекте

**Событие запуска проверок (trigger).**
Проверки запускаются автоматически при двух событиях: `push` в любую ветку репозитория и `pull_request` в ветку `main`.
Это задано в workflow `.github/workflows/student-ci.yml` (строки `on: [push, pull_request]`).
Фактическое событие конкретного запуска видно на странице run в GitHub Actions.

**Автоматический тест.**
В workflow есть отдельный шаг, который запускает `python -m unittest discover -s tests -p test_app.py -v`.
Тесты проверяют контракт приложения: в частности, `test_create_request` ожидает HTTP-статус `201` при создании запроса.
Если реальный код возвращает другой статус, тест падает, и CI становится красным.

**Сборка.**
Сборка выполняется в отдельном job `build`, который зависит от job `test` (`needs: test`).
Команда сборки: `docker build -f lab/Dockerfile -t devops-student:${{ github.sha }} lab`.
Результат сборки - Docker-образ, помеченный SHA текущего run. Это ещё не выпуск: образ существует только на runner'е и исчезает после завершения job, если его не отправить в registry.

**Отдельное решение о выпуске.**
Решение о выпуске принимает человек: после того как CI прошёл зелёным и PR одобрен, выполняется слияние (merge) в `main`.
Только после этого код считается принятым.
Автоматической выкатки на сервер в проекте нет — это осознанное решение, чтобы отделить delivery (артефакт готов) от deployment (артефакт выкачен).

## 2. Схема пути

Место проверки — **после push в короткую ветку и повторно на PR**.
Обратная связь об ошибке появляется **в Actions сразу после push**: если тест или сборка падают,
разработчик видит красный run до того, как создаст PR или выполнит merge.

## 3. Сравнение с Git-flow и обоснование выбора

Git-flow предполагает несколько долгоживущих веток (`main`, `develop`),
а также временные ветки `release/*` и `hotfix/*`. Это оправдано в больших командах с длительным циклом релиза,
когда нужно параллельно поддерживать несколько версий и готовить выпуски поэтапно.

Для небольшой учебной работы такая схема избыточна:
- над проектом работает один человек (или пара), нет параллельных релизных линий;
- цикл изменений короткий: сделал → проверил → слил;
- дополнительные ветки (`develop`, `release/*`) создают бюрократию без пользы: больше merge-конфликтов и больше шагов до обратной связи.

Поэтому выбрана **простая схема**: одна долгоживущая ветка `main` + короткие ветки под конкретные задачи.
Проверка запускается на каждом push и на PR, обратная связь приходит быстро, а решение о выпуске остаётся за человеком.

## 4. Ответ на проверку понимания

Сборка образа (`docker build`) — это **не** автоматический deployment.
Это часть CI: создание артефакта (Docker-образа) и проверка того, что он собирается.
Deployment был бы, если бы образ автоматически отправлялся в registry и выкатывался на сервер без участия человека.
В моём проекте автоматической выкатки нет — есть только сборка и отдельное решение о выпуске.
