# K1-01. Путь изменения

## Схема пути изменения формы заявки
1. **Разработчик**: Пишет код (добавляет поле "Телефон" в форму), обновляет API (чтобы принимать поле) и тесты.
2. **CI (Непрерывная интеграция)**: Запускаются автотесты. Если тесты прошли — образ собирается.
3. **Тестировщик**: Проверяет форму в браузере, отправляет заявку с новым полем. Проверяет, что данные сохраняются в БД.
4. **Эксплуатация (DevOps)**: Деплоит новую версию (например, через Docker Compose) на прод-сервер.
5. **Пользователь**: Открывает сайт, видит новое поле, заполняет и отправляет заявку.

## Риск: где ошибка может остаться незамеченной?
**Место:** Связка «API — База данных».
Разработчик мог обновить HTML-форму и код API, но забыть добавить миграцию базы данных (новый столбец) или обновить SQL-запрос на вставку.
Тестировщик может проверить только UI (что форма отправляется),
 а API может вернуть 200 OK, но данные в базу не запишутся (или запишутся в другое поле).

**Предложенная проверка:**
Интеграционный тест на уровне БД.
 После отправки формы тест должен напрямую сделать запрос
 `SELECT phone FROM requests` и убедиться, что данные там.
 Либо тестировщик вручную проверяет админку/дамп БД после отправки.

## Ответ на проверку понимания
**Почему готовый код ещё не означает работающий сервис?**
Код — это лишь текст. Чтобы он стал сервисом,
 его нужно собрать в исполняемый артефакт (образ),
 настроить окружение (переменные, порты), запустить в инфраструктуре,
 обеспечить сетевую доступность и подключить к базе данных.
 Без этапа эксплуатации (деплоя) код остается просто файлами на диске.
